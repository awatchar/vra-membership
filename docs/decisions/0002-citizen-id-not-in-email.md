# 0002: อีเมลผู้จัดการแสดงเลขบัตรประชาชนแบบปิดบัง

- Status: accepted
- Date: 2026-08-21
- Issue: #13

## Context

Issue #1 หัวข้อ 31 ระบุรายการข้อมูลที่อีเมลแจ้งผู้จัดการต้องแสดง และมี **เลขบัตรประชาชน** อยู่ในรายการนั้น เพราะผู้จัดการต้องใช้เลขนี้กรอกเข้าระบบของสำนักงาน กสทช.

แต่ระบบนี้ออกแบบมาโดยให้เลขบัตรประชาชนเป็นข้อมูลที่ได้รับการป้องกันมากที่สุด: เข้ารหัสด้วย key ที่เปลี่ยนไม่ได้ (หัวข้อ 44), เก็บ keyed hash แยกไว้สำหรับตรวจสมัครซ้ำ, ห้ามอยู่ใน log (หัวข้อ 58) และตาม #16 การถอดรหัสจะเกิดขึ้นเฉพาะเมื่อผู้จัดการเปิดหน้ารายละเอียดใบสมัคร พร้อมบันทึก audit event ของการเข้าถึง

การส่งเลขเต็มทางอีเมลทำให้การควบคุมทั้งชุดนั้นไม่มีความหมาย เลขจะไปอยู่ใน record ของ Resend, ใน mailbox ของผู้จัดการอย่างถาวร, ใน backup ของผู้ให้บริการอีเมล และอยู่ในที่ที่ระบบนี้ลบหรือ audit ไม่ได้เลย โดยไม่มี event ใดบันทึกว่าใครอ่านเมื่อไร

ที่สำคัญคือ **เลขในอีเมลไม่ได้ช่วยให้งานเร็วขึ้น** ผู้จัดการต้องเข้าระบบผู้จัดการอยู่แล้วเพื่อกด "รับเรื่อง" และกดยืนยันการบันทึกทะเบียน (หัวข้อ 32 และ 37) ซึ่งเป็นหน้าเดียวกับที่มีเลขเต็มอยู่

## Decision

อีเมลผู้จัดการแสดงเลขบัตรประชาชนแบบปิดบัง เห็นสี่หลักท้ายในตำแหน่งจริงบนบัตร (`x-xxxx-xxxx0-12-1`) และมีข้อความอธิบายว่าเลขเต็มดูได้ในหน้ารายละเอียดใบสมัคร

การถอดรหัสเพื่อทำ mask ยังบันทึก audit event (`CITIZEN_ID_MASKED_FOR_EMAIL`) เหมือนการอ่านครั้งอื่น ๆ เพื่อไม่ให้ audit trail มีช่องว่างตรงที่มีการส่งอีเมล

ถ้า `PII_ENCRYPTION_KEY` ใช้งานไม่ได้หรือถอดรหัสไม่สำเร็จ อีเมลจะไม่มีแถวนี้เลยแทนที่จะแสดง placeholder และยังส่งออกไปตามปกติ เพราะการที่ผู้จัดการไม่รู้ว่ามีใบสมัครรออยู่แย่กว่าการไม่เห็นสี่หลักท้าย

## Consequences

- สี่หลักท้ายพอให้ผู้จัดการยืนยันว่ากำลังดูคนเดียวกับที่ตรวจใน กสทช. แต่ไม่พอให้ใช้เลขนั้นทำอะไรได้เอง
- ผู้จัดการต้องเปิดหน้ารายละเอียดเพื่อดูเลขเต็ม ซึ่งเป็นขั้นตอนที่ต้องทำอยู่แล้ว
- เลขบัตรประชาชนเต็มไม่เคยออกจากขอบเขตที่ระบบควบคุมและ audit ได้
- เบี่ยงจากตัวอักษรของหัวข้อ 31 หนึ่งจุด และบันทึกไว้ที่นี่เพื่อให้ตรวจย้อนได้
- ถ้าเจ้าของระบบต้องการเลขเต็มในอีเมลจริง ๆ ต้องแก้ code พร้อม decision record ใหม่ ไม่ใช่พลิกด้วย flag เพราะอีเมลที่ส่งออกไปแล้วเรียกคืนไม่ได้

## Alternatives considered

- **ส่งเลขเต็มตามหัวข้อ 31** ตรงตามข้อกำหนดที่สุด แต่ทำให้การเข้ารหัสใน database, การ audit การถอดรหัส และนโยบายห้าม PII ใน log กลายเป็นการป้องกันเฉพาะทางที่มีทางอ้อมเปิดอยู่
- **ไม่แสดงเลขเลย** ปลอดภัยที่สุดและไม่ต้องถอดรหัสในเส้นทางอีเมล แต่ผู้จัดการเสียวิธียืนยันตัวบุคคลอย่างเร็วเมื่อมีชื่อซ้ำหรือชื่อคล้ายกัน
- **ทำเป็น config flag** ให้เจ้าของระบบเลือกได้ แต่ flag ที่ลดระดับการป้องกัน PII เป็นสวิตช์ที่กดผิดได้ง่ายและผลกระทบย้อนกลับไม่ได้
- **แนบเป็นไฟล์ที่ต้องใส่รหัส** ยังเป็นการส่งข้อมูลออกนอกระบบ และเพิ่มขั้นตอนที่ผู้จัดการต้องจัดการรหัสเพิ่มอีกชุด
